# scheduler/

- ESPHome compiles every C and C++ file in this folder into the firmware, so tests, tools and scratch code live elsewhere. Other files, like this one, are fine.
- charger.h, settings.h and the headers they include, calendar.h, market.h, savings.h, schedule.h and tariff.h, are built as plain C++17 by the unit tests, without ESPHome, and as gnu++20 in the firmware. Keep them C++17 and free of ESPHome headers. test/mutation_test.py lists the seven: a new header goes there too.
- The settings are a file on the board, which the page writes (a custom plan goes under `tariff:`, each line indented by two spaces), and which read_settings() in settings.h reads and checks before the board saves it, and again at every start. The settings routes, like ESPHome's own, answer only the board's own page: a request with another Origin gets 400, while curl, which sends none, works. Settings apply at once, and device.yaml's Bluetooth lambda hands a new VIN to the Tesla part; on a board that has a car, any change but the ntfy topic's deletes the schedule, as Delete schedule does, by request (deletes_schedule() in settings.h), while charging now stays; a board that has a car restarts only for another car, market area or currency, by request (restarts() in settings.h, which the settings route asks before it answers): the Bluetooth link and key are the car's, and the prices downloaded already are the area's, in its currency. The page's setup saves its first step's, the prices, as settings without the car's tesla_ lines, which read_settings() takes as no car yet, all three or none: the board then shows No car yet and does nothing until the setup's car step adds them. Without prices, the car charges as usual. A new setting needs its place in read_settings()'s table, its check, and its field in web/web_ui.js, as users have no other way to set it. A check made stricter turns away settings a board saved before: the page then asks for them again.
- Entity names are an interface. The page finds the board's entities by name (web/web_ui.js), this component finds the Tesla's by name, and Ready by and Ready by once are saved under keys ESPHome makes from their names. Renaming an entity, or an ESPHome release that makes those keys differently, silently loses the saved values: check after upgrading ESPHome.
- esphome-tesla-ble, at the pinned `tesla_ble_ref`: the car reports its security state (Asleep, User Present, the locks and the Charge Port Door) to any key, one it doesn't know too, so only a charging report (the Charger, Charging, Battery) shows the key is paired; the "Charger" binary sensor keeps its state once the car has reported it (only the asleep and user-present sensors go back to unknown), until the component clears it for a key the car turned away, as ESPHome calls no callback for the same state again; with the charging state "Unknown" it also reports the Charger as off, which isn't an unplug; the battery level and charge limit keep their last values; the charging states are "Disconnected", "No Power", "Starting", "Charging", "Complete", "Stopped", "Calibrating" and "Unknown". The controller relies on all of these. Its Last Command text sensor, there though Home Assistant hides it by default, reports each of its commands' results, like `Wake → Failed: VCSEC key not on whitelist - pairing required` from a key the car doesn't know: the component then forgets the pairing, and the page brings back the setup's key step until the car reports again. Its polls report no errors, so a key removed in the car shows only when the board's own command fails, by the owner's choice over a change upstream.
- Savings goes to flash byte for byte under the key "scheduler_savings", and ESPHome loads it only into a struct of the same size, which a static_assert holds: another size starts every board's figures afresh, and another layout of the same size misreads them. To change it, read the old layout under its key and save the new one under another.
- Controller::observe_() runs before the schedule is made, so it judges a start from the car against the previous tick's schedule. On the first tick after a restart there's none, and in_schedule_() is true.
